# Kiro CLI

The Kiro CLI's `kiro-cli` TUI, verified as a CREWMATE, SCOUT, PRIMARY, and SECONDMATE adapter on 2026-09-20 with kiro-cli 2.22.1 on Linux.
This is the Amazon-Q-lineage `kiro-cli` binary, NOT the `/usr/bin/kiro` Electron IDE, which never appears as a `kiro-cli` process.
Verified for all four kinds: `../../../../../bin/fm-spawn.sh` accepts a `--secondmate` launch on it, and `../../../../../docs/supervision-protocols/kiro-cli.md` owns its primary wake protocol.

## Operating facts

| Fact | Value |
|---|---|
| Binary | Absolute `kiro-cli` from `PATH`, refused if absent; NOT `/usr/bin/kiro` (the Electron IDE). The process tree carries anchored names `kiro-cli`, an inner `kiro-cli-chat` wrapper, and a `bun` interpreter running the extracted `tui.js`. |
| Launch | V3 (default): a ship, scout, or secondmate runs `chat --v3 -a "<brief>"` on Kiro's default agent (no `--agent`) with `KIRO_DUMP_REQUESTS` set for the worker tool check, the resolved absolute binary, per-task `KIRO_HOME`/`KIRO_DATA_DIR`/`KIRO_CHAT_LOG_FILE`, and task-specific project hook files copied from that `KIRO_HOME`; explicit `FM_KIRO_ENGINE=v2` falls back to `chat --v2 --trust-all-tools --agent firstmate-kiro-v2-<id>` with an embedded-hook agent inside `KIRO_HOME`. The trust flag is part of the correct launch on both engines (see "Turn end and trust"). The brief is a single firstmate-encoded positional query that auto-submits with no extra Enter and stays steerable (verified live on 2026-09-20: an 18 KB multi-line brief ran its first turn, the pane stayed alive on the idle `ask a question or describe a task` prompt, and a later typed message completed a second turn). The INTERACTIVE steerable TUI is used, not the `--no-interactive` one-shot, because every kind must stay alive to be steered and to drive `/no-mistakes` across turns. |
| Busy state | Semantic hooks are the writer: `UserPromptSubmit` opens `busy kiro-hook`, `PreToolUse`/`PostToolUse` publish native progress, and `Stop` closes idle, all generation-bound through `../../../../../bin/fm-busy-event.sh` so a late hook from an older incarnation is rejected; the `kiro-regex` rendered-tail fallback in `../../../../../bin/fm-busy-lib.sh` remains for a pane whose generation is absent. |
| Rendered tail | Busy shows the composer footer `Thinking... (esc to cancel)` beside a braille spinner and the status line `Kiro is working` (`Kiro is working · Type to steer · Ctrl+S to queue`); idle shows the `ask a question or describe a task` placeholder and neither anchor. Both anchors are ASCII that survive `KIRO_ASCII_MODE=1`; the spinner is locale-sensitive and is not a signal. |
| Turn end | A first-class `stop` agent hook, kiro-cli's authoritative turn-end signal, firing at every turn end in both interactive and headless modes and carrying `KIRO_SESSION_ID` - the same Stop-hook shape as claude and cursor. The tracked `../../../../../bin/fm-kiro-turnend-hook.sh` serves BOTH the crewmate/primary turn-ended touch and, for a primary, keeping the doorbell owner (`../../../../../bin/fm-primary-doorbell.sh`) running; see "Turn end and trust" below. |
| Exit | `/quit`, one Enter (or `/exit`); both quit with save. `fm-control exit` types `/quit` only after the shared composer classifier reads the pane empty: kiro-cli's idle placeholder renders in a grey (RGB ~158) above the fleet ghost-strip ceiling, so `../../../../../bin/fm-composer-lib.sh` treats the exact `ask a question or describe a task` text as empty only under the recorded `kiro-cli` identity, and it treats the helper row below the composer as furniture in both of its shapes (V3's `/sessions to resume · /copy to clipboard` and the bare `/copy to clipboard` of an agent launched before the V3 wiring). |
| Interrupt | Single `Escape` cancels the streaming turn and leaves the session alive (the busy footer reads `esc to cancel`); no clear key follows. A single `Ctrl+C` does NOT quit the new default TUI - `Ctrl+C` twice quits - so never rely on one `Ctrl+C` to abort a turn. |
| Skill | `/<skill>`, for example `/no-mistakes`; kiro-cli discovers project skills only in `.kiro/skills`, so Firstmate's agent-only skills reach it through the tracked `.kiro/skills -> ../.agents/skills` symlink (the same shape as `.claude/skills`), beside the user skills under `~/.kiro/skills`. |
| Autonomy | `-a`/`--trust-all-tools` auto-approves every tool call for the run and is part of every Firstmate launch; `--trust-tools=<names>` or empty trusts a narrower set. An agent file's `allowedTools` grants no useful wildcard: `["*"]` still stops on `fs_write`'s Replace in File with an approval dialog (verified live on 2026-09-21), so the launch flag carries the trust, and Firstmate's only agent file, the oracle, names concrete V3 tool ids. |
| Marker | None used for identity. kiro-cli publishes a rich `KIRO_*` environment family (`KIRO_SESSION_ID`, `KIRO_VERSION`, `KIRO_CLI_ACP_CLIENT_NAME`), but those are ordinary inheritable environment state, so `../../../../../bin/fm-harness.sh` identifies it by the anchored process names `kiro-cli`/`kiro-cli-chat` alone. |
| Resume | `--resume-id <SESSION_ID>` resumes an exact session (verified); `--resume` (`-r`) resumes the cwd's most recent conversation; `chat --list-sessions --format json` enumerates sessions. On 2.32.0 V3 conversations persist under the launch's `KIRO_HOME/sessions`, so a plain `kiro-cli chat -a --v3 --resume` without that `KIRO_HOME` (such as a Herdr restart) does not reopen the worker's conversation: it opens a new, empty default-agent session in the worktree with the global knowledge setting and no `invoke_sub_agent`, whose hooks still fire (verified 2026-10-18, `../../../../../docs/verification/runtime-backends.md`). Firstmate uses deterministic relaunch, so no verified pane-resume contract is required, but a resumed session keeps its hooks (see "Hook commands"). |
| Model | `--model <id>`; discover with `chat --list-models --format json`. |
| Effort | `--effort <low\|medium\|high\|xhigh\|max>`, the full shared vocabulary (verified in `chat --help`); `max` is only ever reached through an explicit captain choice. |
| Composer | Bare `›` prompt row with the `ask a question or describe a task` idle placeholder; steering confirms delivery through the `Kiro is working` / `esc to cancel` busy footer (`../../../../../bin/fm-composer-lib.sh`). |
| In-turn steering | A busy ship or scout gets no typed doorbell: its next tool call is held once and the hook prints the new steering records on stderr, the only hook output 2.32.0 shows the model mid-turn (exit-0 stdout of PreToolUse and PostToolUse, plain or JSON, is dropped). Each record is delivered once, never to an oracle tool call, and an idle worker still gets the typed doorbell (`../../../../../bin/fm-kiro-turnend-hook.sh` header, `../../../../../bin/fm-task-inbox-lib.sh` header). Text typed into a busy Kiro composer and submitted is also delivered at the next tool boundary (Kiro's own "Type to steer"). |

## Turn end and trust

kiro-cli declares lifecycle hooks in an agent's JSON config, and the `stop` hook fires at the end of every turn in both interactive and headless modes, delivering `{hook_event_name:"stop", cwd, session_id}` on the hook script's STDIN with `KIRO_SESSION_ID` in the environment; kiro-cli 2.24.1 V3 workspace `Stop` hooks carry no `assistant_response` or other reply text, and `UserPromptSubmit` carries the prompt in `prompt` ([verification](../../../../../docs/verification/supervision.md#kiro-cli-2241-hook-surface-and-process-tree-2026-09-29)).
Note that `KIRO_WORKSPACE_ROOT` was UNSET in live sessions; the hook falls back to `$PWD`, which is the launch directory.
Everything Firstmate needs lives inside a per-task `KIRO_HOME` at `state/<id>.kiro-home`, which `../../../../../bin/fm-spawn.sh` rebuilds fresh on every spawn, so generated payloads and the turn-end pointer are not written into the project's own worktree and no captain-shared file is edited:

- `settings/cli.json` carries `chat.disableTrustAllConfirmation=true`, which suppresses the `--trust-all-tools` startup confirmation dialog `--trust-all-tools` otherwise raises, plus `chat.allowAnimations=false` for a stable screen-scrape baseline.
  The suppression is REQUIRED, not cosmetic: without it the dialog renders `Warning: Kiro is running in trust all tools mode` with its default selection on `No, exit` and the positional brief does NOT run until it is answered, which Firstmate's arrow-less key plane cannot do (verified live on 2026-09-20).
- `agents/firstmate-kiro-v2-<id>.json` exists only for the explicit V2 fallback: the Firstmate-owned embedded-hook agent selected by `--agent`.
  On V3 the hook payload (and a worker's oracle) live under `KIRO_HOME/project/.kiro/`, while cwd-local `.kiro/hooks/fm-firstmate-<id>.json` is a regular byte-for-byte copy required by Kiro's workspace discovery, which ignores symlinked payloads.
  No V3 kind gets a generated agent and the primary has no tracked one: every V3 session runs on Kiro's default agent, which on 2.32.0 offered every file, image, search, write, shell, code, web, and sub-agent tool, while a generated list of CLI aliases had resolved to five tools (`../../../../../docs/verification/runtime-backends.md`).
  A spawn or relaunch removes a `.kiro/agents/firstmate-kiro-<id>.json` an earlier launch left, and cleanup still removes it.
- `.fm-kiro-steer-inject` opts a ship or scout into in-turn steering; `.fm-kiro-subagents/` and `.fm-kiro-doorbell-turn` are that delivery's per-turn markers.
- `.fm-kiro-required-tools` lists, for a ship, scout, or secondmate, the tools it cannot work without (`read_file`, `list_directory`, `file_search`, `grep_search`, `fs_write`, `execute_bash`, plus `invoke_sub_agent` for a worker with an oracle); `requests/` receives Kiro's per-request records, which the worker tool check reads and deletes (`../../../../../bin/fm-kiro-turnend-hook.sh` header).
- `agents/fm-turn-end.d/<token>` is the registry entry naming `state/<id>.turn-ended`, minted per task.
- `.fm-kiro-session` records the generation and Kiro session id of the launched incarnation's latest accepted event; a conversation resumed without `FM_KIRO_BUSY_GEN` writes busy state only under that generation and only for that session id.
- `../../../../../bin/fm-kiro-turnend-hook.sh` is the tracked, shared hook.
  It is a guarded no-op for its turn-ended touch: it touches `state/<id>.turn-ended` ONLY when the isolated-home pointer inside the `KIRO_HOME` its command names carries the token of that home's registry entry, with the old workspace pointer accepted only for migration, so a stray kiro-cli session under this `KIRO_HOME` that is not this task changes nothing.
  For a PRIMARY or SECONDMATE session the same hook additionally keeps the doorbell owner running (falling back to one plain watcher re-arm when no owner can run), which acts only in primary scope (`../../../../../bin/fm-primary-scope-lib.sh`'s `fm_primary_scope_matches`) for the session that owns that home's lock, so a worker's hook stops after its task updates.

`../../../../../bin/fm-teardown.sh` retires the whole `state/<id>.kiro-home` directory with `rm -rf` and it is rewritten fresh on relaunch, so no shared global registry cleanup is needed; `../../../../../bin/fm-control-lib.sh`'s turn-end auth path is therefore empty for kiro-cli, while its wiring paths list the isolated-home `.fm-kiro-turnend` pointer and the `state/<id>.kiro-turnend-token`.

## Opus oracle

A ship or scout worker can ask one hard architecture question of a read-only Opus advisor through Kiro's V3 sub-agent tool (`invoke_sub_agent`, verified on 2.29.0).
Its `name` argument selects a workspace agent by agent-file name, so `../../../../../bin/fm-kiro-lib.sh` installs `firstmate-oracle-<id>`, as a regular copy under `KIRO_HOME/project/.kiro/agents` and the worktree's `.kiro/agents`; `../../../../../bin/fm-spawn.sh` excludes it from git and `../../../../../bin/fm-teardown.sh` removes it with the task hooks.
The default agent reaches it (verified on 2.32.0).
The rule that tells the worker when to consult it rides in a `# Kiro oracle` section of the worker's launch brief, the one Kiro-specific worker guidance surface.
The oracle runs on `claude-opus-5.5` and names V3 tool ids (`read_file`, `list_directory`, `file_search`, `grep_search`, `code`, `web_fetch`, `remote_web_search`), because a sub-agent that listed the aliases `fs_read`, `grep`, and `glob` received none of them.
It carries no write, shell, or sub-agent tool, and permission rules deny the `shell`, `fs_write`, and `subagent` capabilities on top, which hold under `-a`.
A secondmate and the primary get no oracle.
A home whose `config/kiro-oracle` first line is `off` gets no oracle for any worker: no oracle agent, no `invoke_sub_agent` among the required tools, and no oracle rule in the launch brief.
Absent or any other content keeps the oracle on, and the file is home-local and not inherited ([`docs/configuration.md`](../../../../../docs/configuration.md) "Kiro worker oracle").
`../../../../../docs/verification/runtime-backends.md` records the live run and its Opus dispatch evidence, and `tests/fm-kiro-harness.test.sh` pins the grants.

## Hook commands

Verified on kiro-cli 2.22.1 (KAS 0.66.4) on 2026-09-28: Kiro runs each hook command through `/bin/sh` with the session's workspace root as its working directory and a compact JSON payload on stdin carrying `session_id`, `hook_event_name`, and `cwd` first.
It reloads `.kiro/hooks` files while a session runs, applies each hook's 60-second default timeout (a per-hook `"timeout"` in seconds extends it on 2.24.1), fires `SessionStart` only for a conversation's first prompt, and runs no workspace hooks under `--no-interactive`.
Every Firstmate registration therefore reaches `../../../../../bin/fm-kiro-turnend-hook.sh` without the hook's folder or launcher environment: generated task hooks name it by absolute path with `--kiro-home <per-task KIRO_HOME>`, and the tracked primary hook resolves it from the payload's `cwd`, so a linked task worktree that inherits the tracked file runs its own copy and stays inert.
A resumed primary retakes a lock whose recorded pid is not a live harness on its first `UserPromptSubmit`, and the `Stop` re-arm forks into its own session so it never holds the turn end.
`tests/fm-kiro-harness.test.sh` pins these commands from an unrelated folder with a scrubbed environment, and `FM_KIRO_RESUME_LIVE_E2E=1 bash tests/fm-kiro-resume-live-e2e.test.sh` refreshes the live resume evidence.

## Detection

Detected by ancestry alone: `../../../../../bin/fm-harness.sh` matches the anchored process names `kiro-cli` and the inner `kiro-cli-chat`, never `*kiro*`, so `kiroshi` and an unrelated bare `bun` do not match.
No environment marker is promoted: the `KIRO_*` family is inheritable environment state, not identity, and kiro-cli does not clear an inherited `CLAUDECODE` - but a structural kiro-cli ancestor outranks that retained marker, which `../../../../../bin/fm-harness.sh` decides without depending on the spawn's own launch-boundary marker clearing.
`fm_kiro_cli_process_matches` in `../../../../../bin/fm-session-lock-lib.sh` is the one owner of those frame names, used by both detection and the session lock, so a session running on kiro-cli can acquire this home's lock.
Both walks climb the same shared ancestry (`FM_ANCESTRY_MAX_HOPS` there), so detection and the lock name the same session from a shallow tool call and from a hook several wrapper shells deep.
Its interactive session on 2.22.1 is a contiguous four-frame run (`kiro-cli` -> `kiro-cli-chat` -> `bun` -> `kiro-cli-chat`) whose tool subprocesses and `stop` hook both descend from the innermost `acp` frame; on 2.24.1 that innermost frame is a `node` running `acp-server.js` in its own session ([verification](../../../../../docs/verification/supervision.md#kiro-cli-2241-hook-surface-and-process-tree-2026-09-29)), so the lock walk reports the whole run and anchors on the stable OUTERMOST `kiro-cli` frame rather than the transient inner engine pid.

## Worker busy state and turn end

`../../../../../bin/fm-spawn.sh` arms a busy generation for kiro-cli and passes it to the hook as `FM_KIRO_BUSY_GEN`, which always wins over the session record above; `../../../../../bin/fm-kiro-turnend-hook.sh` applies `busy` on `UserPromptSubmit`, progress on `PreToolUse`/`PostToolUse`, and `idle` on `Stop`, each bound to the task by the isolated-home pointer and per-`KIRO_HOME` token before any state mutation (verified live on 2026-09-21 by `tests/fm-kiro-signals-live-e2e.test.sh`).
`fm_busy_kiro_tail_busy` matches the `Thinking... (esc to cancel)` and `Kiro is working` anchors (with the `FM_BUSY_KIRO_REGEX` override) as the fallback when no generation is recorded, and `fm_busy_classify` reports `unknown kiro-regex` rather than idle when they are absent, because a long turn can scroll them out of the captured tail.
The authoritative turn-end signal is the `stop` hook above, not this rendered fallback; `state/<id>.turn-ended` remains a wake notification for the watcher rather than current-state truth.

## Primary integration

SUPPORTED: `../../../../../docs/supervision-protocols/kiro-cli.md` owns the wake protocol.
kiro-cli's `Stop` hook fires and is awaited synchronously, but exit 2 and a `followup_message` are no-ops, and the one continuation 2.24.1 honors (a `{"decision":"block"}` reply) fires once with no further `Stop`, so it cannot keep the primary supervised across turns; it only keeps the doorbell owner running.
The structural path is external: `../../../../../bin/fm-kiro-primary.sh` launches the V3 primary on Kiro's default agent with the tracked `.kiro/hooks/fm-firstmate.json`, the `SessionStart` hook runs the digest into context and publishes the pane as `state/.primary-endpoint`, the `UserPromptSubmit` and `Stop` hooks keep that record current every turn for the lock-owning session (hooks that arrive after a conversation's first prompt never see `SessionStart`), the hooks keep one detached doorbell owner running (`../../../../../bin/fm-primary-doorbell.sh`), the only component that rings this pane ([watcher continuity](../../../../../docs/watcher-continuity.md#kiro-doorbell-owner)), and the `UserPromptSubmit` hook attaches the drained queue as that turn's context; the foreground `../../../../../bin/fm-watch-checkpoint.sh` remains the fallback when no endpoint is published, and `../../../../../docs/turnend-guard.md` records the limitation.
ACP: kiro-cli 2.22.1 exposes two client-driven surfaces (`kiro-cli acp`, an Agent Client Protocol agent over stdio taking `--agent`, `--model`, `--effort`, `-a`, and `--agent-engine v3`; and `chat --output-format stream-json`, which emits the run's ACP events as JSON Lines and implies `--no-interactive`), and the V3 TUI itself talks to its engine over an inner `kiro-cli-chat acp` frame.
Firstmate does not drive ACP directly: a stdio ACP agent has no pane to steer, observe, or ring, so it would need a Firstmate-side ACP client, a second permission plane, and a second wake protocol beside the durable queue and doorbell, while `stream-json` is one-shot and cannot be steered across turns; the steerable V3 TUI in a pane therefore stays the verified surface, and its rendering is read through the shared composer and busy classifiers.

## Current-state observability

A Kiro coordination's `fm-crew-state` read can report `unknown` with `source=none` even while its live TUI and routed supervision cycle are healthy.
This is a documented adapter limitation rather than a new state writer defect because Kiro exposes lifecycle hooks and rendered activity but no structured current-state publication that `fm-crew-state` can consume for the coordination pane.
The watcher therefore relies on the Kiro hook signals, status events, endpoint liveness, and the coordination home's summary ledger rather than treating the Kiro panel as current-state authority.
